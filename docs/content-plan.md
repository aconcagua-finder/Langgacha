## 1. Проблема, которую решаем

Текущее состояние seed-пула: **150 слов** (75C / 45UC / 20R / 10SR / 0 SSR), плоские теги (`básico`, `verbo`, `ciudad`...), бустеры тянут случайное слово из пула по рарности.

### Почему это тупик

- **Тепличная повторяемость.** 150 слов × 7 карт в бустере = любое слово статистически встречается каждые 1-2 бустера. Это маскирует проблемы SRS/XP/ветхости — проверить работает ли TASK-048 (Word XP + интервалы) на таком пуле нельзя. Это не "недоделанный прототип с данными", это "прототип без данных".
- **На 5000 слов текущая модель разваливается.** `pickRandomWord` в `backend/src/modules/cards/cards.generator.ts:84` делает `skip = random * count` по всему пулу. На 3500 C-слов игрок получает случайные несвязанные слова: `cocina → oficina → quirófano`. Никакого контекста, никаких ассоциативных цепочек. Ветхость разъедает 5000 слов равномерно, игрок не успевает. SM-2 из TASK-048 работает на уже известном материале, а не когда каждое слово встречается впервые.
- **Quiz-дистракторы не семантичны.** `quiz.generator.ts:105-110` берёт дистракторы из buckets по типу/рарности — на маленьком пуле случайно попадают из той же темы, на большом — не попадут никогда. Это превращает квиз из "проверь знание" в "угадай на глаз".
- **Теги сейчас — мусор.** `básico` висит на 43 словах из 150. Ничего не группируется.
- **Нет механики "ввода нового материала".** Бустер = 7 случайных карт. Для гачи ок, для педагогики — плохой паттерн: человек не должен встречать 7 новых слов без контекста.

### Что нужно для разблокировки

Трёхслойная таксономия + добавление CEFR + тематические бустеры + семантичные дистракторы + поэтапная набивка базы с постоянным ревью и контрольными точками.

## 2. Архитектурное решение: трёхслойная таксономия

```
Domain (4-6 больших жизненных сфер)
  └── Theme (25-35, конкретные ситуации — "на кухне", "в отеле", "small talk")
       └── Word / Concept (20-60 слов в каждой теме)
```

### Примеры доменов и тем (черновик, финализируем в TASK-049)

| Domain | Themes (примеры) |
|--------|------------------|
| **Everyday** | Home, Kitchen, Morning routine, Weather, Clothing, Body & health |
| **City** | Public transport, At the bank, Shopping, Navigating, Post office |
| **Social** | Meeting people, Small talk, Disagreement, Party, Family relations |
| **Travel** | Hotel, Airport, Restaurant abroad, Emergencies, Asking directions |
| **Work** | Office basics, Meetings, Email, Job interview, Remote work |
| **Expression** | Idioms A1, Idioms B1, Slang Argentina, Lunfardo (спец-домен для SR/SSR) |

### Плюс "Core" — ядро без темы

~200 слов: артикли, местоимения, базовые глаголы (ser/estar/haber/tener/ir/hacer/poder...), числа, дни недели, базовые прилагательные, союзы. Они доступны с нулевого уровня, не привязаны к теме.

### Почему это работает

1. **Повторения честные.** Бустер тянется "в теме" — 7 карт из темы `Kitchen`. SM-2 работает внутри темы из 30-60 слов — игрок реально встречает их несколько раз за неделю.
2. **Quiz-дистракторы семантичны.** Правильный ответ `sartén/сковорода`, дистракторы `olla/кастрюля`, `cuchillo/нож` — настоящая проверка различения.
3. **Прогрессия читается.** "Я освоил тему 'Завтрак', открыл 'Обед'". Сейчас цель абстрактная — "собрать всё".
4. **Тематические бустеры = SKU.** Стандартный бустер — случайная тема из разблокированных. Тематический — выбранная тема за пыль. Это и монетизация, и педагогика.
5. **Естественные контейнеры для будущих фич:** рейд-боссы тем, ачивки тем, карточки правил как награда за освоение темы, матчмейкинг PvP по темам.
6. **Дубли концептов между темами — фича.** `agua` может быть в `Kitchen`, `Restaurant`, `Morning routine` — так реально работает контекстное обучение. В коде: `Theme ↔ Concept` many-to-many.

## 3. CEFR как отдельная ось

**Рарность (C/UC/R/SR/SSR) и CEFR (A1/A2/B1/B2/C1/C2) — ортогональны.**

- Рарность = игровая ось (редкость, колорит, "крутость карты")
- CEFR = образовательная ось (сложность усвоения, требуемый уровень)

Пример: `laburar` — R по рарности (арг. сленг), A2 по CEFR. `obsolescencia` — SR по колориту, C1 по CEFR.

### Как используется CEFR

Доступность слова = пересечение `unlockedRarities` ∧ `unlockedCefrLevels`.

- Игрок A1 не получает B2+ слов даже C-рарности (он не готов грамматически).
- Игрок B1 всё ещё получает A1-A2 слова (повторение основы).
- SSR с идиомой уровня C1 — доступен только B1+ игроку, но это гача-мечта, а не блокировка обучения.

CEFR добавляется полем `cefrLevel` на модель `Word`.

## 4. Объём базы

**Целевой размер: ~5000 слов** для испанского MVP.

Ориентир: активный словарь B1 ≈ 2000, B2 ≈ 4000, C1 ≈ 8000. 5000 покрывает A1-B2+ с запасом — больше чем нужно, но меньше чем "зачем нам C1".

### Распределение

| Категория | Кол-во | Комментарий |
|-----------|--------|-------------|
| **Core (без темы)** | ~200 | Служебные слова, базовые глаголы, числа, дни |
| **Themes A1** | ~1500 | 15 тем × ~100 слов, бытовая база |
| **Themes A2-B1** | ~2500 | 15 тем × ~150 слов, расширенный бытовой + социальный |
| **Themes B1+** | ~500 | 5 тем × ~100 слов, работа, абстрактное |
| **Expresiones / идиомы** | ~300 | Отдельный пул R/SR/SSR, разблокируется на B1+ |
| **Итого** | ~5000 | |

Распределение по рарностям (приблизительно, для генератора):

- C: ~55% (~2750)
- UC: ~25% (~1250)
- R: ~13% (~650)
- SR: ~5% (~250)
- SSR: ~2% (~100)

## 5. Архитектурные решения (зафиксировано)

### 5.1. Схема БД (план миграции, детали в TASK-050)

**Новые сущности:**

```prisma
model Theme {
  id            String    @id @default(uuid())
  key           String    @unique         // "kitchen", "hotel", "small-talk"
  nameRu        String                    // "На кухне"
  nameEs        String                    // "En la cocina"
  domain        String                    // "Everyday", "Travel", ...
  cefrTier      String                    // минимальный CEFR: "A1"/"A2"/...
  orderIndex    Int                       // порядок показа
  description   String?                   // короткое описание темы для UI
  emoji         String?                   // эмодзи-аватар темы
  createdAt     DateTime  @default(now())
  words         WordTheme[]
}

model WordTheme {
  wordId        String
  themeKey      String
  word          Word      @relation(fields: [wordId], references: [id], onDelete: Cascade)
  theme         Theme     @relation(fields: [themeKey], references: [key], onDelete: Cascade)
  isPrimary     Boolean   @default(false) // основная тема слова vs вторичная
  @@id([wordId, themeKey])
}
```

**Изменения в `Word`:**

```prisma
model Word {
  // ... существующие поля ...
  cefrLevel     String?   // "A1" | "A2" | "B1" | "B2" | "C1" | "C2"
  themes        WordTheme[]
  isCore        Boolean   @default(false)  // слова без темы (ядро)
}
```

**Почему many-to-many, а не одно поле `themeKey`:**
- Одно слово может естественно жить в нескольких темах (`agua` в Kitchen + Restaurant + Morning routine)
- `isPrimary` даёт "главную" тему для UI показа и прогресса
- Гораздо гибче на будущее (рейд-боссы по теме, ачивки и т.п.)

### 5.2. Бустеры (план изменений в boosters.service.ts)

```typescript
type OpenBoosterParams = {
  playerId: string;
  themeKey?: string;  // если задан — тематический бустер
}
```

- Стандартный бустер: выбирается случайная разблокированная тема (по CEFR уровню игрока), все 7 карт из неё + шанс 1 карты из Core
- Тематический бустер: все 7 карт из указанной темы (стоит пыль, 1/день лимит)
- Идиомы-бустер: разблокируется на B1+, тянет из домена `Expression`

Гарантия UC+ и pity SR+ сохраняются.

### 5.3. Quiz-дистракторы (план изменений в quiz.generator.ts)

Приоритет при выборе дистракторов:
1. Слова из той же темы (primary theme правильного слова)
2. Слова из того же домена
3. Слова того же типа (Persona/Lugar/...)
4. Остальные

Это превращает reverse-quiz в осмысленную проверку, особенно на больших пулах.

### 5.6. Диалект: Rioplatense Spanish (аргентинский/уругвайский)

**Решение (2026-04-09, Aleksei):** LangGacha — это проект про **аргентинский испанский** (Rioplatense). Это первоклассное проектное решение, фиксируется тут.

**Что это значит в коде и в контенте:**

1. **Все flavorText** используют voseo как нейтральную форму: `vos tenés`, `vos sos`, `vos hablás`, а не `tú tienes`, `tú eres`, `tú hablas`.
2. **Все hint/мнемоники** могут ссылаться на аргентинский узус и культурный контекст.
3. **Все quizOptions** (перевод и дистракторы) соответствуют аргентинскому смыслу в первую очередь. Если слово значит разное в Аргентине и в Испании — берём аргентинское значение (`boliche` = "ночной клуб", а не "боулинг").
4. **Базовые C-слова остаются нейтрально понятными** — это не противоречит voseo. `casa`, `agua`, `libro` — международны. Но если у слова есть аргентинский и кастильский вариант (`carro` vs `coche`, `celular` vs `móvil`, `papa` vs `patata`) — берём аргентинский.
5. **Lunfardo и rioplatense-сленг** — осознанная часть проекта, не странное исключение. Они живут в домене `Expression`, темах `slang-rioplatense` и `idioms-everyday`.
6. **Voseo в C-рарности — это ОК**, вопреки черновой рекомендации из первого аудита. Раньше была записана рекомендация "C = нейтральный литературный без voseo" — **она отменена** этим решением. Новое правило регистров см. ниже.

**Новое правило регистров (заменяет черновое из audit):**

| Рарность | Что допустимо |
|----------|---------------|
| C | Voseo, нейтральная лексика, повседневный разговорный стиль. НЕТ специфического сленга или lunfardo. |
| UC | Voseo + лёгкие разговорные обороты. Могут быть вкрапления lunfardo если слово широко понятно (`che`, `dale`, `re` как интенсификатор). |
| R | Voseo + разговорный + характерные регионализмы. Может быть сленг, если слово само — сленг. |
| SR/SSR | Полный спектр lunfardo, идиомы, архаичные словечки. |

**Важно про понятность:** аргентинский ≠ недоступный. Большая часть C-слов (`casa`, `agua`, `libro`, `comida`...) всё равно будут понятны испаноговорящим из других стран. Voseo и аргентинский узус влияют в основном на **глагольные формы** (`vivís` вместо `vives`) и на **выбор синонимов** (`laburar` > `trabajar` там где нейтрально по смыслу).

**Будущее расширение на кастильский испанский:**

Через `conceptKey` (см. `project_multilang_plan.md` в memory). Когда решим добавить кастильский — каждая карта с аргентинским словом получит параллельную кастильскую: `celular (AR) ↔ móvil (ES)`, `papa (AR) ↔ patata (ES)`. Картинки переиспользуются. Сейчас архитектура уже готова к этому через `conceptKey` и `language`. **Но в рамках Content Foundation мы НЕ делаем кастильский.**

**Реализация в схеме БД:** поле `language` уже есть в Word (`"es"`). Это будет означать "rioplatense". Когда добавится кастильский — будет `"es-ar"` / `"es-es"` или аналогичный код, плюс миграция существующих записей на `"es-ar"`. Пока оставляем просто `"es"` — не дёргаем миграцию из-за будущего расширения.

### 5.7. Инструмент генерации контента

**Решение (2026-04-09, Aleksei):** контент генерируется **этим агентом** (Claude Opus через Claude Code) — интерактивно или через субагенты в рамках сессий. **НЕ используем** внешние API (ChatGPT, Claude API отдельно, другие LLM), НЕ запускаем батчевые прогоны вне текущего инструмента.

**Следствия:**
- Каждая тема — отдельная TASK, обрабатывается в рамках сессии с ручным ревью
- Большие темы (~80-100 слов) можно делить на подпакеты (~25-30 слов за шаг) если нужно из-за объёма сессии
- Субагенты можно использовать для параллельной работы (напр. два субагента на две темы одновременно), но каждый работает через тот же Claude Code инструментарий
- **Никакой отдельной инфраструктуры для генерации не строим.** Нет скриптов "batch-generate via API", нет отдельных прогонов с ChatGPT.

**Why:** Aleksei хочет максимальный контроль, ревью каждого шага и единый инструмент. Внешние API были бы быстрее, но терялся бы контроль качества и было бы сложно интегрировать в существующий workflow с TASK-файлами.

## 6. Ревизия существующих 150 слов

**Критически важно:** ревизия ДО генерации нового, не после.

### Что проверяем

- **flavorText** — естественность, грамматическая корректность, контекст
- **hint (мнемоника)** — работает ли ассоциация, не грубая ли, не притянутая за уши
- **quizOptions** — дистракторы не слишком очевидные, нет синонимов правильного ответа, семантически в теме
- **translationRu** — точность, не слишком широкое/узкое толкование
- **conceptKey** — консистентность, англ. ключ отражает реальный концепт
- **tags** — выбросить все текущие теги, заменить на тему + CEFR

### Что делаем с 150 существующими

Раскладываем по темам новой таксономии. Если слово не подходит ни в одну тему — оно либо идёт в Core (служебное), либо в очередь "уточнить" (может подсказать, что нужна ещё одна тема).

150 слов становятся эталоном для AI-промпта при генерации новых тем.

## 7. Подход к генерации через AI

**Мы не будем запускать "сгенерируй 5000 слов" одной командой.** Это гарантированно каша.

### Эталонная тема вручную (TASK-051)

Первая тема (кандидат: `Kitchen`) собирается вручную в диалоге между Aleksei и агентом:
- 60-100 слов
- Каждое слово — с обоснованием выбора (почему это слово, а не другое)
- Проверка на пропущенные "очевидные" слова темы
- Калибровка flavor-стиля на этой теме
- Калибровка квизов и дистракторов (все тематические, на вариациях)

Этот блок → эталон для промпта AI на следующие темы.

### Итеративная генерация (TASK-052..)

По одной теме за задачу:
1. Агент готовит черновик темы (AI-генерация по эталонному промпту)
2. Автоматические проверки (скрипт): нет дублей слов, все quiz-опции валидны, все слова уникальны, CEFR помечен, тема помечена
3. Ручное ревью Aleksei перед мёрджем
4. Мёрдж в отдельный seed-файл `seed-theme-<key>.ts`
5. Запуск миграции + перегенерация Prisma client

### Контрольная точка (TASK-055 или когда наберём ~500 слов суммарно)

После 5-7 тем останавливаемся. Aleksei играет неделю. Проверяем:
- Реально работает SRS?
- Тематические бустеры не душные?
- Квизы осмысленные?
- Что полировать в таксономии?

Если ок — жмём дальше. Если нет — правим, потом дальше.

## 8. Что явно НЕ делаем сейчас

- **Картинки** — агент не генерит изображения. Откладываем на будущее, используем fallback на emoji/placeholder как сейчас.
- **TTS** — откладываем.
- **Эволюция дубль-концептов** — архитектура позволяет, но сейчас не реализуем. Эволюция остаётся в рамках одной карты (`canEvolve` + `isEvolved`).
